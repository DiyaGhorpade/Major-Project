# Money Plant Monitoring: Backend

FastAPI + SQLAlchemy 2 + SQLite service (port 8000) that serves the bundled sensor dataset to the
dashboard and, from Phase 2 on, runs it through the ML service (`money_plant_ml_pipeline`, port 8001).

**Status: Phase 1** (skeleton, config, database, startup seeding, `/api/health`). Pipeline run, ML client,
read APIs and the remaining routers are stubs that later phases fill in.

## Setup and run

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env            # optional; every value has a default
.venv/bin/uvicorn app.main:app --port 8000
```

On startup the app creates the tables and seeds the bundled dataset
(`money_plant_ml_pipeline/data/raw/plant_sensor_data.csv`, 5,376 rows) in about a second.
Seeding is idempotent: restarting inserts nothing new. If seeding fails or times out, the error is logged and the
app still starts. Then open <http://127.0.0.1:8000/docs> or `curl localhost:8000/api/health`.

Tests: `.venv/bin/pytest -q` (temp SQLite DBs; the dataset fixtures use the real CSV and a crafted bad CSV).

Reset the database: stop the app and delete `data/app.db*`.

### Configuration (`.env`, see `.env.example`)

`ML_SERVICE_URL`, `DATASET_PATH`, `ML_CONFIG_PATH`, `ML_REPORTS_DIR`, `ML_ARTIFACTS_DIR`, `DATABASE_URL`,
`ML_TIMEOUT_S`, `ML_CONCURRENCY`, `EXPLAIN_MODE`, `HISTORY_ROWS_DEFAULT`, `CORS_ORIGINS`, plus `SEED_TIMEOUT_S`
(default 120) and `LOG_LEVEL`. Relative paths and SQLite URLs resolve against `backend/`, never the cwd.

### Database and migrations

The app always runs `Base.metadata.create_all` at startup, so a fresh clone needs no migration step.
Alembic (`app/db/migrations`, initial revision `0001`) exists for **future schema changes**:
`.venv/bin/alembic upgrade head` on a new DB, or `.venv/bin/alembic stamp head` once on a DB the app already created.
After editing `models.py`: `.venv/bin/alembic revision --autogenerate -m "..."`.

## Layout

See `docs/backend_implementation_master_prompt (1).md` section 4.1. Implemented so far: `core/` (config, logging,
errors, mappings, plant catalog), `db/` (engine, models, repositories, migrations), `services/seed_service.py`,
`api/deps.py`, `api/routes/health.py`, `main.py`. All other modules are placeholders with a docstring stating their purpose.

## Deviations

From `docs/PHASE0_FINDINGS.md` (the real code/data differ from the master prompt):

- **DEV-1** History length: the backend sends `min(max_history_rows, max(required_rows, 60))` prior rows, not the full history (features only look back 48 rows; `max_history_rows` is read from the ML `config.yaml`, `required_rows` from `/metadata`).
- **DEV-2** SHAP: the ML service gives top-5 contributions with no base value, so `base_value`/`model_output` are null; global SHAP is read from `reports/` once generated by the ML pipeline's own evaluation script (it ships empty).
- **DEV-3** Node mapping: the CSV wins. Odd plants are node 1, even plants node 2 (not "pots 1-12 / 13-16").
- **DEV-4** `Plant.samplingPoint` is not a fixed pot position in the data (it cycles 1-12 per reading), so it is the latest reading's multiplexer channel, nullable.
- **DEV-5** `TulsiCondition` is data-backed: Healthy / Water / Light / Temperature-Humidity / Mixed / Unclassified Stress. "Nutrient Stress" is removed because the dataset has no nutrient data (Cluster 4 is the temperature/humidity group).
- **DEV-6** `SensorRecord` soil/temperature/humidity/light are nullable. Missing values stay NULL and the row is `flagged`, never filled.
- **DEV-7** New frontend recommendation category `monitoring` (ML `general` / `model_confidence`); `superseded` is added to recommendation statuses.
- **DEV-8** Plant names, species, descriptions, locations and optimal ranges are not in the dataset; they come from the static Tulsi catalog in `app/core/plant_catalog.py` (user decision to keep the Tulsi branding).

Phase 1 implementation decisions (not in the docs):

- **DEV-9** `sessions` has a surrogate `id` plus unique `session_id` (readings reference `session_id`), and extra columns `flagged_records` and `node_expected` (per-node expected counts, derived from the data's cadence).
- **DEV-10** `received_at` / `accepted_at` are NULL for dataset rows (the Jetson receipt time is unknowable); `record_id` (`R-<id>`) is a derived property, not a stored column.
- **DEV-11** Local validation adds an `invalid:` issue (non-numeric sensor cell, value stored NULL). Rows with an unparseable timestamp or a plant id outside 1-16 are dropped and counted (not stored); a repeated `(plant_id, timestamp)` keeps the first row.
- **DEV-12** Default settings: `collection_times` is the dataset's real schedule (12 two-hourly IST slots), not the mock's 08:00/13:00/18:00; `storage_path` is the SQLite file path. `soil_adc_dry`/`soil_adc_wet`, `jetson_receiver_port`, polling interval, log retention and `ph_sensor_installed` are editable placeholders (the mock's values), not measured calibration or observed hardware settings.
- **DEV-13** Optimal ranges: lower bounds mirror the ML recommendation thresholds; upper bounds (soil 75 %, humidity 90 %) are plain horticultural choices because the ML config has none.
- **DEV-14** Storage shape: `ml_predictions` keeps `probabilities` as JSON plus `severity`/`confidence` instead of `p_*` columns; `devices` carries `channels`, `role`, `simple_role` (no hardware JSON; unknown hardware fields are derived as null later).
- **DEV-15** KMeans label is `Environmental state group <id>` using the raw id (no +1 shift).
- **DEV-16** Global SHAP comes from `reports/<run_id>/evaluation_<UTC>/shap_global_importance.json`, produced once by `scripts/generate_explanations.py` (no retraining). That file holds only mean |SHAP| per feature, so `beeswarm_points` come from `shap_sample_explanations.csv` (50 test rows × top 5 features) and are labelled as a sample.
