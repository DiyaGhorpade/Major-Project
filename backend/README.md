# Money Plant Monitoring: Backend

FastAPI + SQLAlchemy 2 + SQLite service (port 8000) that serves the bundled sensor dataset to the
dashboard and, from Phase 2 on, runs it through the ML service (`money_plant_ml_pipeline`, port 8001).

**Status: complete.** All read APIs, sensor ingestion, the Run pipeline (`POST /api/pipeline/run` + status polling),
ML-driven recommendations and the frontend wiring are implemented and covered by tests. The whole stack is started from
the repository root with `./scripts/dev.sh` (see the root `README.md`); this file is the backend reference, including the
numbered **Deviations** from the original spec below. "Frontend type changes required (deferred to Phase 4)" further down
is kept as a history of what changed; those type changes are done.

## Setup and run

Easiest: `./scripts/dev.sh` from the repository root does all of this (venvs, deps, ML service, backend, frontend);
`make seed` seeds the DB without servers. Manually:

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env            # optional; every value has a default
.venv/bin/uvicorn app.main:app --port 8000
```

On startup the app creates the tables and seeds the bundled dataset
(`money_plant_ml_pipeline/data/raw/plant_sensor_data.csv`, 5,376 rows) in about a second.
Seeding is idempotent: restarting inserts nothing new. If seeding fails or times out, the error is logged and the
app still starts. Then open <http://127.0.0.1:8000/docs> or `curl localhost:8000/api/health`.

Tests: `.venv/bin/pytest -q` (temp SQLite DBs; the dataset fixtures use the real CSV and a crafted bad CSV; the ML
service is faked, except `tests/test_ml_integration.py`, which uses the real service at `ML_SERVICE_URL` and skips if it is down).

### ML service (needed for Run)

```bash
cd money_plant_ml_pipeline
python3 -m venv .venv && .venv/bin/pip install -r requirements-tested.txt   # sklearn 1.9 / numpy 2.5 / xgboost 3.4 / shap
PYTHONPATH=src .venv/bin/python -m uvicorn plant_ml.api.main:app --host 127.0.0.1 --port 8001 --workers 4
```

`--workers 4` matters (DEV-18): the service is CPU/GIL-bound, so one worker serves ~20 predictions/s whatever the backend
concurrency; four workers cut a full Run from ~5 min to ~80 s. Global SHAP is a one-off setup step (no retraining):
`cd money_plant_ml_pipeline && .venv/bin/python scripts/generate_explanations.py --input data/raw/plant_sensor_data.csv --run-id <run_id from artifacts/latest.json>`.

Run: `curl -XPOST localhost:8000/api/pipeline/run` (optional body `{"reset": true}`), then poll `GET /api/pipeline/status`.
Check DEV-1 yourself with `.venv/bin/python scripts/verify_history_equivalence.py` (ML service must be up).

Reset the database: stop the app and delete `data/app.db*`.

### Configuration (`.env`, see `.env.example`)

`ML_SERVICE_URL`, `DATASET_PATH`, `ML_CONFIG_PATH`, `ML_REPORTS_DIR`, `ML_ARTIFACTS_DIR`, `DATABASE_URL`,
`ML_TIMEOUT_S`, `ML_CONCURRENCY`, `EXPLAIN_MODE`, `HISTORY_ROWS_DEFAULT`, `CORS_ORIGINS`, plus `SEED_TIMEOUT_S`
(default 120) and `LOG_LEVEL`. Relative paths and SQLite URLs resolve against `backend/`, never the cwd.

### Database and migrations

The app always runs `Base.metadata.create_all` at startup, so a fresh clone needs no migration step.
Alembic (`app/db/migrations`, initial revision `0001`) exists for **future schema changes**:
`.venv/bin/alembic upgrade head` on a new DB, or `.venv/bin/alembic stamp head` once on a DB the app already created.
After editing `models.py`: `.venv/bin/alembic revision --autogenerate -m "..."`.

## Deviations

From `docs/PHASE0_FINDINGS.md` (the real code/data differ from the master prompt):

- **DEV-1** History length: the backend sends `min(max_history_rows, max(required_rows, 60))` prior rows, not the full history (features only look back 48 rows; `max_history_rows` is read from the ML `config.yaml`, `required_rows` from `/metadata`).
- **DEV-2** SHAP: the ML service gives top-5 contributions with no base value, so `base_value`/`model_output` are null; global SHAP is read from `reports/` once generated by the ML pipeline's own evaluation script (it ships empty).
- **DEV-3** Node mapping: the CSV wins. Odd plants are node 1, even plants node 2 (not "pots 1-12 / 13-16").
- **DEV-4** `Plant.samplingPoint` is not a fixed pot position in the data (it cycles 1-12 per reading), so it is the latest reading's multiplexer channel, nullable.
- **DEV-5** `TulsiCondition` is data-backed: Healthy / Water / Light / Temperature-Humidity / Mixed / Unclassified Stress. "Nutrient Stress" is removed because the dataset has no nutrient data (Cluster 4 is the temperature/humidity group).
- **DEV-6** `SensorRecord` soil/temperature/humidity/light are nullable. Missing values stay NULL and the row is `flagged`, never filled.
- **DEV-7** New frontend recommendation category `monitoring` (ML `general` / `model_confidence`); `superseded` is added to recommendation statuses.
- **DEV-8** Plant names, species, descriptions, locations and optimal ranges are not in the dataset; they come from the static Tulsi catalog in `app/core/plant_catalog.py` (user decision to keep the Tulsi branding).

Phase 1 implementation decisions (not in the docs):

- **DEV-9** `sessions` has a surrogate `id` plus unique `session_id` (readings reference `session_id`), and extra columns `flagged_records` and `node_expected` (per-node expected counts, derived from the data's cadence).
- **DEV-10** `received_at` / `accepted_at` are NULL for dataset rows (the Jetson receipt time is unknowable); `record_id` (`R-<id>`) is a derived property, not a stored column.
- **DEV-11** Local validation adds an `invalid:` issue (non-numeric sensor cell, value stored NULL). Rows with an unparseable timestamp or a plant id outside 1-16 are dropped and counted (not stored); a repeated `(plant_id, timestamp)` keeps the first row.
- **DEV-12** Default settings: `collection_times` is the dataset's real schedule (12 two-hourly IST slots), not the mock's 08:00/13:00/18:00; `storage_path` is the SQLite file path. `soil_adc_dry`/`soil_adc_wet`, `jetson_receiver_port`, polling interval, log retention and `ph_sensor_installed` are editable placeholders (the mock's values), not measured calibration or observed hardware settings.
- **DEV-13** Optimal ranges: lower bounds mirror the ML recommendation thresholds; upper bounds (soil 75 %, humidity 90 %) are plain horticultural choices because the ML config has none.
- **DEV-14** Storage shape: `ml_predictions` keeps `probabilities` as JSON plus `severity`/`confidence` instead of `p_*` columns; `devices` carries `channels`, `role`, `simple_role` (no hardware JSON; unknown hardware fields are derived as null later).
- **DEV-15** KMeans label is `Environmental state group <id>` using the raw id (no +1 shift).
- **DEV-16** Global SHAP comes from `reports/<run_id>/evaluation_<UTC>/shap_global_importance.json`, produced once by `scripts/generate_explanations.py` (no retraining). That file holds only mean |SHAP| per feature, so `beeswarm_points` come from `shap_sample_explanations.csv` (50 test rows × top 5 features) and are labelled as a sample.

Phase 2 implementation decisions:

- **DEV-17** DEV-1 is verified: for 64 readings (12 plants, cold start to row 335, 55 with nulls in the reading or its 60-row history) `history_rows=60` and 500 give identical label, probabilities, cluster, anomaly score/flag and recommendation ids (max diff <= 1e-9); 10 rows does differ, so the check is sensitive. Reproduce with `scripts/verify_history_equivalence.py`. The default therefore stays 60.
- **DEV-18** Throughput: the ML service is GIL-bound, so `ML_CONCURRENCY` only helps if the service runs several uvicorn workers. Measured (320 items): 1 worker 21.6/s at concurrency 1, 18.4/s at 4; 4 workers 18.8/s at 1, 41.5/s at 4. Start the ML service with `--workers 4` (dev.sh should).
- **DEV-19** Run semantics: `pipeline_runs.total` is the number of readings that still need a prediction in that run (5,376 on a first/reset run, 0 on a no-op re-run, which completes at 100%). Without `reset`, `ok` predictions are skipped only if made by the current ML `run_id` (a retrained model recomputes), `rejected` ones are skipped, `unavailable` ones are retried (an `unavailable` outcome never replaces an existing `ok` prediction, whatever its model run: the old row stays until a new `ok`/`rejected` result replaces it), and a latest-reading prediction lacking an explanation is redone when explainability is available. `runId` is the integer row id. A run that finds some readings `unavailable` (but not an outage) still ends `completed` and says so in `message`.
- **DEV-20** ML client timeouts: a batch call uses `6 x ML_TIMEOUT_S` (up to 64 predictions per request); health checks use one 2 s attempt and are cached 5 s (`/metadata` 60 s) so `/api/health` and `/api/pipeline/status` stay fast; the run's preflight health check does retry 3 times.
- **DEV-21** The advisory ML `/validate` of the seeded data runs once in a background task after startup (single request: the endpoint has no size limit) and never blocks or fails startup. Its summary is stored in `model_info.metadata_json["dataset_validation"]`; the same JSON column holds the full `/metadata` document (run_id, model_version, trained_at, label_mapping, feature names, required rows, disclaimer, ...).
- **DEV-22** The nullable JSON columns of `ml_predictions` use `JSON(none_as_null=True)` so "no value" is SQL NULL (queryable with `IS NULL`), not the JSON text `null`. No schema change.
- **DEV-23** Outage handling: 3 consecutive batches that are entirely unavailable stop the run (`failed`, message names the cause); those readings are stored as `unavailable` (error text kept) and everything before them stays saved. Worker crashes (bugs, DB errors) end the run as `Internal error: <ExceptionType>` (details only in the server log); only `MLUnavailable` becomes `unavailable` and `MLRejected` becomes `rejected`. The on-demand `POST /api/predictions` never stores an outage but does store a rejection. Typed error envelopes: `ml_unavailable` (503) and `ml_rejected` (422).
- **DEV-24** Stored rejection text keeps the ML reason and flagged rows, e.g. `invalid_readings: ... [row 5: soil_out_of_range]`. `plants.status` is derived from the latest prediction at the end of the run (DEV-27). Unit tests point `ML_SERVICE_URL` at a closed port so a real ML service on 8001 cannot leak into them.
- **DEV-25** Run the backend as a **single process** (one uvicorn worker): the no-double-run guard is an in-process asyncio lock plus the DB, and startup marks every `queued`/`running` run as failed ("interrupted by restart"), which would kill another process's live run. `reset=true` deletes all predictions and anomaly records *before* recomputing, so an ML outage after a reset leaves some readings with no prediction at all (the run is `failed`; a plain re-run fills them). The same applies to recommendations: `reset=true` also deletes the untouched ones before recomputing, so a reset run that fails leaves them absent (user-modified ones stay) until a later successful run rebuilds them.
- **DEV-26** Other Phase 2 details: `EXPLAIN_MODE=none` also forces `explain=false` on `POST /api/predictions` (otherwise the request's `explain`, default true, is honoured); a new `ok` result without an explanation keeps the stored one of the same model run, and an upsert with no `pipeline_run_id` keeps the existing one; the on-demand route reads `/metadata` from a 60 s cache and holds no DB session across the ML call; ML requests for a chunk are built lazily from shared per-plant lists; a non-503 5xx from `/predict/batch` falls back to per-item `/predict` (a failing item becomes `unavailable`, "ML internal error"); non-positive `max_history_rows`/`max_batch_items` in the ML YAML fall back to 500/64 with a warning; `SQLite busy_timeout` is 10 s; `current_plant_id` is the first plant of the most recently started chunk; prediction `envState.distance` stays null rather than 0 when missing.

Phase 2b (recommendations) decisions:

- **DEV-27** Lifecycle: one active (`new`/`in_progress`) recommendation per `(plant, category)`, built from the plant's *latest reading with an `ok` prediction* at the end of every run. A re-run updates an active one in place (content, `source_reading_id`, `prediction_id`, `updated_at`) and never touches its `status` or `user_modified`. A recommendation for the same `(plant, category, source reading)` that the user closed (`completed`/`dismissed`) stays closed, so re-running unchanged data is a no-op (no new rows, no status or `updated_at` change); a newer reading creates a new `new` one. Active ones whose category is no longer produced become `superseded` only if `user_modified` is false (a superseded one whose condition returns is revived to `new`); user-touched ones are left as they are. A plant with no `ok` prediction keeps its recommendations and gets `plants.status = unmeasured`. `reset=true` deletes untouched recommendations and keeps user-modified ones (status intact, `prediction_id` cleared); the rebuild then matches and updates them. `recommendations.prediction_id` is now `ON DELETE SET NULL`. **Migration 0001 was edited in place** (nothing is deployed), so an existing `app.db` created before this change must be deleted and re-seeded. `reset=true` removes the untouched recommendations *before* recomputing predictions, so if that run fails (e.g. ML outage) they stay absent until a successful run. Duplicate-active protection: `PATCH` to `new`/`in_progress` on a closed or superseded recommendation returns `409 conflict` (details `activeId`) while another active one exists for the same plant and category; and the sync repairs any such duplicate defensively: it keeps the user-modified (then newest) active row, deletes an untouched duplicate that owns the reading the kept row must move to, supersedes other untouched duplicates, and only logs a warning if several are user-modified. An on-demand `POST /api/predictions` that stores an `ok` prediction for a plant's latest reading refreshes that plant's recommendations and `plants.status` immediately.
- **DEV-28** Priority is `high|medium|low` as in the TS type; an ML or rule priority of `critical` (none is sent today) is mapped to `high`. Heuristic escalation to `high`: latest severity `high`, or `moderate` with the 3 most recent consecutive `ok` predictions all `moderate`/`high`. It raises an ML recommendation of the type's category (`stress_type_guess`: Water -> irrigation, Light -> lighting, Temperature/Humidity -> climate, Mixed -> all present condition categories) and says why in `reason`; with none present it adds a heuristic one (`monitoring` for Unclassified, "Sustained stress: ..." titles). Escalation is skipped when the latest reading is an anomaly or the ML service sent `verify_sensor`/`retake_reading`/`low_confidence` (it designs those cases as "do not infer plant stress from this reading"). The anomaly rule adds a heuristic `sensor_check` ("Sensor check") only when no ML recommendation already covers that category; sensor-check reasons quote the anomaly score and the four sensor values but no model stress probability and no plant-health wording.
- **DEV-29** API shape: `GET /api/recommendations` returns a bare JSON list (the frontend expects `Recommendation[]`), total in the `X-Total-Count` header (exposed through CORS); filters `plantId, status, priority, category, source, includeSuperseded` (default false; an explicit `status=superseded` still lists them), `limit` (1-500, default 100), `offset`; order high -> low priority then newest. `PATCH /api/recommendations/{id}` takes `rec-<n>` or `<n>` and a status in `new|in_progress|completed|dismissed` (`superseded` is system-only); optional fields (`updated_at`, `resolved_at`, `confidence`, `mlRecId`) are emitted as `null`, not omitted. `basedOn.runId` is the ML artifact run id (string), not the pipeline run row id. `supporting_sensor_values` is computed on read from the source reading and the plant's optimal ranges (not stored); Light outside the ML config's `recommendations.daytime_hours` (default 9-16, local IST hour of the reading) has no target: status `good`, target `"night (no target)"` (`attention` if the value is missing). The "recent average" skips nulls and values listed under `out_of_range` in the reading's `validation_error`. If the predicted class is missing from `probabilities`, the reason prints `confidence=<x>` instead of `P(<class>)=<x>`. `plantId` is bounded by the plant catalog (1-16), `offset` by 100000, and ids longer than 12 digits are a 404. `scientificContext` is static generic horticulture text per category; `reason` cites only stored numbers (latest value, "recent average" over up to 6 readings when at least 3 are non-null, model P of the predicted class). A cold-start prediction (ML warning containing "cold start" or fewer than 48 prior rows sent) gets "Lower reliability: limited history for this plant." appended.

Phase 3 (read APIs and ingestion) decisions:

- **DEV-30** `Plant.conditionPrediction` comes from the plant's latest *ok* prediction (the one `plants.status` derives from; its `timestamp` says which reading it describes). Besides `condition` (heuristic stress-type guess, `conditionSource:"heuristic"`), `severity`, `probabilities`, `confidence`, `modelVersion` and `simpleExplanation` (generated from stored numbers only) it carries `recordId`, `envState {id,label,distance}` and `anomaly {isAnomaly,score}` as separate labelled fields; `null` when the plant has no ok prediction. `Plant.latestReading` is `null` only for a plant with no readings; `samplingPoint` is the latest reading's channel.
- **DEV-31** Ingestion (`POST /api/sensors/readings`, single object or `{"readings":[...]}` up to 500): Pydantic validates the shape (422 envelope, nothing stored; `plant_id` 1-16, `node_id` 1/2, `sampling_point` 1-12, `timestamp` an ISO string, naive = IST, no NaN/inf). Values are then checked with the seed's `validation_issues` (missing / out-of-range -> stored `flagged`, never clipped). Duplicates on `(plant_id, timestamp)` (compared as instants, also within a batch and against dataset rows) are reported as `duplicate` and not inserted (first wins). Response 201, or 200 when every reading was a duplicate. Extra fields (`rssi`, `crc_ok`, ...) are ignored, not stored (no columns). A `session_id` that is not a known session (sessions only come from the dataset) is stored as NULL and the row is flagged `unknown_session: <id>`. Known sessions get their received/flagged counts and end time recomputed. Prediction is a FastAPI background task after the response: skipped when the ML service is down (`cached_health`), stops at the first outage, and only a plant's newest reading is requested with `explain=true`. A later Run predicts anything that was skipped.
- **DEV-32** Sessions: `node_progress[n].status` is derived (`completed` when received >= expected; otherwise `failed` for a finished session, `in_progress`/`waiting` for a running/scheduled one); `scheduled_at/started_at/ended_at` are nullable; `flagged_records` is added; `duration_seconds` = ended - started.
- **DEV-33** Devices: statuses are always `unknown` (a stored `demo` would be mapped to `unknown`); `hardware_details.model` is a generic label ("Edge gateway" / "ESP32 sensor node") because the data names no hardware; every other hardware field and `ip_address`, `mac_address`, `last_heartbeat` are null; ESP32 `channels` = distinct sampling points seen on that node; the gateway's `last_transmission` is the newest reading overall; extra fields `readingCount` and `plantIds`.
- **DEV-34** Settings: `PUT` takes any subset, ignores unknown/legacy keys (`api_base_url`, `demo_mode`), uses strict types (a string is not accepted for an int/bool), and ranges: polling 1-3600, port 1-65535, ADC >= 0, retention 1-3650, `collection_times` `HH:MM` (max 96). `GET`/`PUT` return 503 if the settings row is missing (seed never ran).
- **DEV-35** Model performance reads `artifacts/latest.json` -> `<run>/classifier.meta.json` (+ anomaly/clustering meta) from `ML_ARTIFACTS_DIR` (a file read, not the ML service, so the run it shows is the newest *trained* run even if the service has not been restarted). The result is cached in `model_info.metrics` per `run_id` and re-read when `latest.json` names a new run. `precision`/`recall` are macro means; `laymanStatus` bands on F1 (>=0.75 "Recognised fairly reliably...", >=0.5 "Partly reliable...", else "Often confused..."), always about the synthetic test set. 503 `model_artifacts_unavailable` if the files are unreadable.
- **DEV-36** `GET /api/monitoring/overview` is cached in-process and keyed on a DB fingerprint (`repositories.state_token`: reading / prediction / anomaly / recommendation counts and ids, plant statuses, latest run) plus explicit clears after ingestion, on-demand predictions and each pipeline chunk, so a finished Run, an ingestion or a recommendation change refreshes it. The `pipeline` block is always live. `recentAlerts` mixes the latest anomalies and active high-priority recommendations, ordered by the *reading* time (not creation time), max 10. `clusterSummaries` are experimental groups (averages over each plant's latest reading, nulls ignored), never KMeans clusters. `GET /api/monitoring/plants/{id}` `predictionHistory` has mixed case on purpose (`record_id` snake, the rest camel) as specified.
- **DEV-37** AI: local SHAP is the plant's newest stored explanation (top-5 features only; `observed_value` nullable; `base_value`/`model_output` null; direction `towards/away_from_predicted_class` -> `increases/decreases_prediction`, contribution 0 -> `neutral`); 404 `explanation_unavailable` when none. Global SHAP is the newest `reports/<current run>/evaluation_*/shap_global_importance.json` (else the flat file); 404 `global_shap_unavailable` with `details.hint` = the exact `generate_explanations.py` command. `sample_count` is 500 (the script explains `min(500, test rows)`; `evaluation.json` does not record it, and a `shap_sample_count`/`shap_rows`/`n_explained` key would win). `beeswarm_points` come from the 50-row sample CSV: `feature_value_norm` is the per-feature min-max of `value` (null if the value is missing or constant), `shap_value` the signed contribution, `plant_id` null. Insights are cached like the overview (plus the ML health flags and the report file's mtime).
- **DEV-38** Lists: `GET /api/sensors/readings`, `/api/data-logs`, `/api/predictions`, `/api/ai/anomalies` return a bare JSON array plus `X-Total-Count` (prediction items are camelCase except `record_id` and `plant_id`, which the contract names literally); readings are newest first unless `order=asc`; `limit` default 100 (max 1000; anomalies 500), `offset` <= 100000; `from`/`to` are inclusive ISO-8601 (naive = IST; a `+` decoded to a space is repaired). `q` matches plant id, session id, node id, sampling point, `R-<id>` and the IST timestamp text (substring, case-insensitive). `format=csv` streams every matching row (no cap, `limit`/`offset` ignored) with `ml_*` (model output; `ml_status=not_run` when there is no prediction) and `dataset_label_*` columns kept apart.

Phase 3 audit fixes:

- **DEV-39** Missing SHAP data is an HTTP 404 with the error envelope, not a 200 empty payload: `GET /api/ai/shap/{plant_id}` -> `explanation_unavailable` (plant exists, no stored explanation yet; unknown plant -> plain `not_found`) and `GET /api/ai/shap/global` -> `global_shap_unavailable` with `details.hint` = the exact `generate_explanations.py` command (also when the report is unreadable). The frontend maps both to its empty state. `GET /api/ai/insights`, `/api/ai/anomalies` and `/api/predictions` answer 200 with empty/zero payloads before a Run.
- **DEV-40** `POST /api/predictions` returns the same shape as a `GET /api/predictions` item (`PredictionListItem`, one mapping in `prediction_service.to_item`). The Phase 2 extras (`explanation`, `mlRecommendations`, `historyRowsSent`) are gone from the response: the explanation is at `/api/ai/shap/{plant_id}`, recommendations at `/api/recommendations`.
- **DEV-41** Ingestion changes: an explicit `node_id` that disagrees with the plant's node is stored as sent and flagged (`node_mismatch: expected 1`). A reading is a duplicate only if its `(plant_id, timestamp)` exists: the insert is `ON CONFLICT (plant_id, timestamp) DO NOTHING`, so any other integrity failure is a 500 envelope and rolls the whole request back (no savepoints: pysqlite commits on `RELEASE SAVEPOINT`, which would break that atomicity). The inserted ids, plant ids and "is this the plant's newest reading" flags are computed once per request and handed to the background prediction task (no per-reading lookups); only the affected sessions are recounted.
- **DEV-42** The plant catalog copy is neutral and condition-independent (variety text + the pot's role in the experiment + generic care guidance); pot names end in "Control Group / Watering Trial / Light Trial / Climate Trial" and locations in "... Trial Row/Box" instead of describing a state ("Thirsty", "Shaded", "Drought"). A test rejects verdict words (healthy, thriving, optimal, wilting, ...). The group labels ("Cluster 1: Healthy Control") are experimental-design names and unchanged. Re-seeding refreshes the stored copy.
- **DEV-43** Cache keys: `ml_predictions` gained `updated_at` (bumped on every in-place re-prediction; migration 0001 edited in place as in DEV-27, so an `app.db` from before this change must be deleted) and `repositories.state_token` includes `max(ml_predictions.updated_at)` and `max(recommendations.updated_at)`. The response cache is also cleared explicitly after ingestion, every pipeline chunk and completion, any `POST /api/predictions` (including the rejected path that stores a `rejected` row) and `PATCH /api/recommendations/{id}`. `PUT /api/settings` needs no clear: settings are not part of any cached payload.
- **DEV-44** The ML YAML (history/batch limits, daytime hours) is parsed once per file version (cache keyed on path + mtime; a request costs one `stat`, and the async prediction path does it in a worker thread). A missing or invalid file/value logs a warning (once per file version) and uses the documented default instead of failing silently.
- **DEV-45** No absolute server paths in responses: `source.path` of the global SHAP report is repo-relative (`money_plant_ml_pipeline/reports/<run>/evaluation_<UTC>/shap_global_importance.json`), `details.artifactsDir` of the model-performance 503 likewise, and the default `storage_path` setting is `backend/data/app.db` (existing databases keep what they stored).
- **DEV-46** One rule for "usable sensor value" (`services/sensor_values.py`: not null and not listed under `out_of_range` for that metric), used by the recommendation "recent average" and the dashboard cluster averages (the cluster averages used to include flagged out-of-range values). One number format (`core/units.format_value`): lux 0 decimals with thousands separators, `%` and `°C` 1 decimal, any other unit 2 decimals (this makes SHAP sentences show e.g. `0.46 kPa` instead of a different rounding).
- **DEV-47** `GET /api/plants`, `/api/sessions` and `/api/devices` accept `limit` (default 100, max 500) and `offset` and send `X-Total-Count`; the defaults return everything today (16 / 4 / 3 items).
- **DEV-48** Non-finite numbers (NaN, Infinity) in the SHAP report, its CSV or a stored explanation never reach a response: such features, per-class entries and beeswarm points are dropped, and a non-finite observed value becomes `null`.

Phase 5 (dev experience):

- **DEV-49** `scripts/dev.sh` / `dev.ps1` need Python >= 3.12 because the pinned ML dependencies (`requirements-tested.txt`: numpy 2.5, scipy 1.18, xgboost 3.4, shap 0.54) require it (3.13 preferred, it is what they were tested on); the backend alone would run on 3.11. Both venvs use the same interpreter. A hash of the requirements file (plus the Python version) in `.venv/.deps-hash`, and of `package-lock.json` in `node_modules/.dev-lock-hash`, makes re-runs skip installs.
- **DEV-50** `dev.sh` generates the global SHAP report once when `reports/<run_id>/evaluation_*/shap_global_importance.json` is missing (explanation only, never training; failure is a warning), refuses to start when a port is busy, and never trains.
