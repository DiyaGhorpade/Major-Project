# Sensor ingestion verification

Verified in software on 19 October 2026: **189 tests passed, 24 subtests passed**
using Python 3.12, Flask 3.1.3, pytest 9.1.1, hypothesis 6.170.2, and host `g++`.
No physical Jetson, ESP32, or LAN delivery was verified. Existing collected CSV
files and local Wi-Fi credentials were not modified by the tests.

Hardware handover preparation added configuration-only tests on the same date:

## Reproduce the checks

From the repository root, create a Python virtual environment if needed and
install the ingestion test dependencies:

```text
python -m venv .venv
```

Activate it (`.venv\Scripts\Activate.ps1` on Windows or
`source .venv/bin/activate` on Linux), then run:

```text
python -m pip install Flask==3.1.3 pytest==9.1.1 hypothesis==6.170.2 tzdata
python -m pytest sensor_data_reciever/tests hardware-code/tests -q
```

`g++` must be on PATH for the firmware integration checks. If it is absent,
pytest skips those checks; a passing run with skips does not establish the
firmware-to-receiver path. All output CSVs are created in temporary directories.
No deployment, physical device, Wi-Fi configuration, or acquisition scheduler is
required for this software run.

Scheduled collection is now covered by mock node HTTP servers, completion
tracking, timeout, duplicate, scheduling and lock tests; see [scheduler setup](SCHEDULER.md).

## Evidence and coverage

| Check | What is verified |
| --- | --- |
| Actual sketch generation | Both production `.ino` files compile/run against host sensor and Arduino mocks in both pacing modes. Tests capture the actual bodies passed to `HTTPClient.POST`, rather than recreate them in Python. |
| Validation and storage | Each valid scan supplies 12 node-1 rows and four node-2 rows to the production Flask handler, validator, and real CSV writer. Every field is compared with the captured body. |
| Real local HTTP | Captured firmware bodies travel over loopback TCP to the production Flask application. Each HTTP 200 is followed by CSV readback. The server uses a free local port; the firmware adapter's port 5000/path `/upload` are checked separately by its mocks. |
| Simultaneous nodes | 32 requests from both pacing modes arrive concurrently, including first-file creation. There is one header, 32 complete rows, and 32 distinct UUID4 IDs. Local plant/sensor IDs remain separate through `node_id`. |
| Malformed input | Invalid UTF-8, bad quoting, multiple records, multiline fields, headers, wrong field counts, empty timestamps, invalid/unknown node IDs, invalid numbers, non-finite readings, and out-of-range values return 400 without changing the data file. Valid uploads work afterward. |
| Source diagnostics | Rejections log the claimed third-field `node_id` when it can be recovered, including structurally short records. Missing/unrecoverable identity is `unknown`. It is payload metadata, not authenticated device identity. |
| Jetson metadata order | Controlled-clock and file-operation checks establish `received_at -> validation -> record_id -> accepted_at -> write -> flush -> fsync -> HTTP 200`. Rejected records get no approval timestamp or UUID. |
| Schema and failures | Exact stored column order, UTC metadata, restart appends, and UUID4 identity are checked. Empty, legacy, or reordered existing headers fail startup/upload without modification. Open/write/flush/sync failures return 500, with later requests still usable. |
| Standalone utility | `storage.py` retains its separate nine-field format. Its tests cover CSV round-trip, append/reinitialization, and concurrent writes; the HTTP metadata path is verified independently. |

For example, the first valid record generated by each sketch under the host
mocks is:

```text
0,7,1,1,1,50,23.50,61.25,512.00
0,7,2,1,1,50,23.50,61.25,512.00
```

The stored header is exactly:

```text
record_id,received_at,accepted_at,timestamp,session_id,node_id,sampling_point,plant_id,soil,temperature,humidity,light
```

The last nine stored values match the generated record. The first three are
receiver-assigned UUID4, UTC receipt time, and UTC validation approval time.
Device `timestamp=0` remains uptime; it is not rewritten as UTC. Current global
sensor/plant bounds are preserved; this work does not add node-specific wiring
restrictions or the proposed twelve-field Rev. 3 extension.

## Physical Jetson smoke check — still pending

1. On the Jetson, run the updated receiver with Flask installed. Select a fresh
   output file so the repository's incompatible legacy CSV is preserved:

   ```bash
   cd sensor_data_reciever
   python3 receiver.py --output sensor_data_verification.csv
   ```

2. From another machine on the same LAN, substitute the actual Jetson IP and
   send the two example firmware-generated rows above:

   ```bash
   curl -i http://<JETSON_LAN_IP>:5000/health
   curl -i -H 'Content-Type: text/plain' --data-binary '0,7,1,1,1,50,23.50,61.25,512.00' http://<JETSON_LAN_IP>:5000/upload
   curl -i -H 'Content-Type: text/plain' --data-binary '0,7,2,1,1,50,23.50,61.25,512.00' http://<JETSON_LAN_IP>:5000/upload
   curl -i -H 'Content-Type: text/plain' --data-binary '0,7,2,1,1,nan,23.50,61.25,512.00' http://<JETSON_LAN_IP>:5000/upload
   ```

3. Expect 200 for health and the two valid uploads, then 400 for the non-finite
   reading. Inspect `sensor_data_verification.csv` on the Jetson: starting from a
   new file, there must be exactly two data rows, distinct UUIDs, UTC receipt and
   approval times, the exact header above, and node IDs `1` and `2`. The rejected
   upload must add no row; the console should identify `node='2'`.

4. For actual ESP32 commissioning, use the current
   [commissioning checklist and results template](../docs/hardware_commissioning.md),
   especially C10 for the existing scheduler's `--once` command. Do not add a
   firmware caller or use the manual example rows above as sensor evidence.
   Capture target builds, serial/receiver logs, command ordering and the final
   scheduler journal separately from software test results.

HTTP 200 means append, flush, and `fsync` completed. A 500 or lost response can
occur after some or all bytes reached disk, so it does not prove non-delivery.
Repeated uploads get new IDs; deduplication, buffering, and record retries are
not implemented. Host mocks do not exercise ESP32 Wi-Fi/TCP behavior, target-core
compilation, physical sensors, or Jetson hardware storage durability.
